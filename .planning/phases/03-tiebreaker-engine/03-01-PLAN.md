<objective>
Build the foundational, pure data layer the entire tiebreaker engine depends on: per-team conference win/loss/opponent aggregation (`deriveConferenceRecords`), the frozen raw-win-percentage base ordering (`computeBaseOrdering`), and the Big 12-only overall win count with the FCS win cap (`deriveOverallWinCount`). This is greenfield -- `shared/` does not exist in the repo yet.

Purpose: every later plan in this phase (steps.ts, engine.ts, rules.ts, acc.ts, and all four conferences' fixtures) reads `ConferenceRecord`/`BaseOrdering` values produced here. Getting the NaN-guard (Pitfall 4) and the frozen-once-per-call discipline right here prevents silent corruption everywhere downstream. This module is also the DRY seam Phase 5's standings engine must import rather than re-deriving win/loss tallying (PROJECT.md's DRY constraint).
Output: `shared/domain/tiebreakers/{types,records,baseOrdering}.ts` plus their test files.
</objective>

    - A team present in `teamIds` but appearing in zero of the supplied games still gets a zero-value ConferenceRecord entry (wins:0, losses:0, gamesPlayed:0).

  <action>

  <behavior>
    - computeBaseOrdering groups teamIds into best-to-worst buckets by winPct; teams with equal winPct land in the same bucket; teamIds within a bucket are ordered ascending by id for determinism.
    - deriveOverallWinCount counts each team's total wins across every game they appear in (conference and non-conference), but caps wins credited against non-FBS opponents (any team id not present in `knownFbsTeamIds`) at `fcsWinCap` (default 1) per team -- additional FCS wins beyond the cap add zero further credit, per the Big 12 policy's verbatim text: "Only one win against a team from the NCAA Football Championship Subdivision or lower division will be counted annually."
  </behavior>
  <action>
    Add `type BaseOrdering = readonly TeamId[][]` to types.ts. In baseOrdering.ts implement `computeBaseOrdering(records: ReadonlyMap<TeamId, ConferenceRecord>): BaseOrdering` -- group teamIds by exact `winPct` value, sort the resulting buckets descending by that value, sort teamIds ascending within each bucket. Doc comment must cite PITFALLS.md Pitfall 4's circularity trap explicitly ("computed once per resolution call, frozen, never recomputed mid-procedure").

    In records.ts add `deriveOverallWinCount(allSeasonGames: readonly Game[], outcomes: ReadonlyMap<GameId, TeamId>, knownFbsTeamIds: ReadonlySet<TeamId>, fcsWinCap: number = 1): ReadonlyMap<TeamId, number>`. For each game, look up the winner via outcomes; if the losing team's id is in `knownFbsTeamIds`, credit one win unconditionally; if not (an FCS/non-FBS opponent), only credit the win if the winner's FCS-win count used so far is below `fcsWinCap`, then increment that per-team counter. Doc comment must state this helper is scoped ONLY to Big 12's `total-wins` step (RESEARCH.md Open Question 3's resolution) and is NOT part of the shared conference-scoped `ConferenceRecord` contract -- Phase 5's standings engine must not call this for its own win totals.
  </action>
