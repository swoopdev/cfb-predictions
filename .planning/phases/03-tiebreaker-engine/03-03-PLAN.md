    - Given a synthetic 3-team, 3-step test procedure where step 1 separates nobody, step 2 separates one winner from the remaining two, and step 3 (on the restart with the remaining two) fully separates them: the resulting trace has exactly 2 cycles. Cycle 1 contains 2 StepOutcome entries (step 1 with separated:false, step 2 with separated:true), outcome:'restart'. Cycle 2 contains 1 StepOutcome entry (step 3... actually step 1 of the 2-team procedure, since a restart returns to step one), outcome:'resolved'.
    - A group of size 1 resolves immediately with an empty trace and no step evaluation.
    - When every step in the procedure is exhausted without any separated:true outcome, the result is status:'needsUserInput' with tiedTeams equal to the full remaining group and trace containing one cycle with outcome:'exhausted'.

    - The final resolved order for a 4+ team fixture that runs through 2+ restart cycles contains no duplicate team ids and its length equals the original tied-team count.

  <action>
    Add to types.ts: `TiebreakerCycle = { tiedTeams: readonly TeamId[]; steps: readonly StepOutcome[]; outcome: 'resolved' | 'restart' | 'exhausted'; removed: readonly { teamId: TeamId; reason: 'seeded' | 'eliminated'; atStep: TiebreakerStepId }[] }`; `TerminalReason = { code: 'ranking-step' | 'needs-scores' | 'draw'; ruleCitation: string; sourceName: string }`; `TiebreakerResult = { status: 'resolved'; order: readonly TeamId[]; trace: readonly TiebreakerCycle[] } | { status: 'needsUserInput'; tiedTeams: readonly TeamId[]; reason: TerminalReason; trace: readonly TiebreakerCycle[] }`.

    In engine.ts implement `resolveTiedGroup(tiedTeams: readonly TeamId[], defineTiedTeams: (baseOrdering: BaseOrdering, records: ReadonlyMap<TeamId, ConferenceRecord>, alreadyCommitted: ReadonlySet<TeamId>) => readonly TeamId[], procedureFor: (size: number) => readonly TiebreakerStepId[], baseOrdering: BaseOrdering, records: ReadonlyMap<TeamId, ConferenceRecord>, overallWinCounts: ReadonlyMap<TeamId, number> | undefined, alreadyCommitted: ReadonlySet<TeamId>, terminalReason: TerminalReason, cycles: TiebreakerCycle[] = []): TiebreakerResult`. Note this task's function takes `defineTiedTeams` and `terminalReason` as plain parameters (not a `ConferenceRules` object) so this task's tests are provably conference-agnostic; Task 2 wires the real `CONFERENCE_RULES` entries through these same parameters.

    Base case: if `tiedTeams.length === 1`, return `{ status: 'resolved', order: tiedTeams, trace: cycles }` immediately -- no step evaluation.

    Main loop: iterate `procedureFor(tiedTeams.length)`; for each stepId call `evaluateStep(stepId, tiedTeams, baseOrdering, records, overallWinCounts)`; push the StepOutcome onto a per-cycle `steps` array (D-07: record every attempted step, including separated:false ones). If `!outcome.separated`, continue to the next step in the loop (the "continue on no separation" branch -- do not restart). If `outcome.separated`, take `outcome.partition[0]` as `winners` and flatten every remaining bucket into `restCandidates`; if `winners.length === tiedTeams.length` (should not happen by construction, but guard it) treat as unresolved and continue. Push a cycle with `outcome: winners.length + restCandidates.length === tiedTeams.length && restCandidates.length === 0 ? 'resolved' : 'restart'` and a `removed` entry per winner (`reason: 'seeded'`). If `restCandidates.length === 0`, this cycle fully resolved this group's internal order -- return `{ status: 'resolved', order: winners, trace: cycles }` (note: for this task's generic tests, `winners` may itself have length > 1 if the step's top bucket had a tie; that is acceptable -- it means this step alone did not fully separate the top bucket into a single team, so do not mark `outcome: 'resolved'` in that case; only mark resolved when `winners.length === 1 && restCandidates.length === 0`). Otherwise, compute `nextAlreadyCommitted = new Set([...alreadyCommitted, ...winners])`, compute `nextTiedTeams = defineTiedTeams(baseOrdering, records, nextAlreadyCommitted)`, assert `nextTiedTeams.length < tiedTeams.length` and throw `new Error('resolveTiedGroup: restart did not strictly shrink the tied group -- infinite recursion guard tripped')` if not, then return `prepend(winners, resolveTiedGroup(nextTiedTeams, defineTiedTeams, procedureFor, baseOrdering, records, overallWinCounts, nextAlreadyCommitted, terminalReason, cycles))` where `prepend` merges `winners` ahead of whatever the recursive call's `order`/result produces (for a 'resolved' recursive result, concatenate arrays; for a 'needsUserInput' recursive result, the overall result is that same needsUserInput result -- the already-seeded `winners` are not part of the tied/blocked group, but the overall championship orchestration in Task 2 is what actually consumes `order[0]` for a specific slot, so this function's `order` field on the resolved path should be the full concatenated ranking).

    If the `for` loop over `procedureFor(...)` completes without ever hitting a `separated: true` outcome, push a cycle with `outcome: 'exhausted'` and `removed: []`, and return `{ status: 'needsUserInput', tiedTeams, reason: terminalReason, trace: cycles }`.

    Document both invariants explicitly in a code comment above the function: (a) every recursive call receives a strictly-smaller `nextTiedTeams` than its caller's `tiedTeams`, enforced by the throw above; (b) an eliminated/seeded team never re-enters a later cycle, enforced structurally because `nextAlreadyCommitted` only grows and `defineTiedTeams` is contracted to exclude every id in it. Cite D-09 and PITFALLS.md Pitfall 3 in the comment explaining why restarts re-invoke `defineTiedTeams` rather than reusing the flattened partition remainder directly -- this is what makes the ACC's per-restart tied-team redefinition (Pitfall 3) work correctly with the exact same recursive core the other three conferences use.
