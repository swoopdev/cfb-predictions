regression test that would have caught CR-01, and no user-visible silent-failure surface in
the sidebar or the tiebreaker orchestrator.

This is a corrective gap plan, not a new MVP slice. It adds no user-facing capability and
deliberately manufactures no UI work: Phase 5's user story is already shipped, it is simply
wrong. `StandingsTable.vue`'s rendering contract and `StandingsSidebar`'s props shape are
unchanged.

<design_decision>
## The tie-bucket decision (explicit, per the gap brief)

**Chosen: the standings layer consumes the engine's OUTPUT (`ChampionshipResult.seed1.order`
and `seed2.order`) as its tie definition. It does not import, re-derive, or reimplement any
tie-defining predicate.**

Rationale:

1. `seed1.order` *is* the engine's tied group for the championship spot, already resolved
   into an order. `rules.defineTiedTeams` produced that pool — win percentage for
   SEC/Big Ten/Big 12 via `defineBucketTiedTeams`, the alternate-schedule-length rule for
   the ACC via `defineAccTiedTeams` — and `resolveTiedGroup` returns every member of it in
   final order. Reading `order` therefore gives the standings layer the engine's exact tie
   definition without a second copy of it anywhere. This is strictly more DRY than exporting
   a bucket function for reuse (CLAUDE.md: standings and tiebreaker logic each have exactly
   one implementation), and it is literally what D-11/D-14 describe: "Phase 5 consumes
   Phase 6's resolved-result output and uses it to rank the standings table."
2. It satisfies the CR-01 regression invariant **by construction**, not by coincidence: the
   engine-placed teams are emitted at the top of the table in `order` sequence, so the
   indices of `seed1.order` within the rows are 0, 1, 2, ... and the resolved champion is
   always row 0.
3. It preserves D-04 as the gap brief requires. Every member of a resolved seed group shares
   **one** rank number and the engine orders them *within* it — the tie is never split. Two
   teams with identical conference records always land in the same group (identical records
   imply identical win percentage and identical wins/losses, so `defineBucketTiedTeams` and
   `defineAccTiedTeams` both make the same membership decision for them), so D-04's literal
   guarantee — identical conference records show the same rank number — still holds.
4. It has the smallest blast radius of the candidate designs. Exactly one existing test
   encodes the old semantics and needs rewriting; the other eight ranking tests keep their
   current assertions verbatim.

**Rejected — reimplementing the ACC rule in the standings layer.** Forbidden by CLAUDE.md's
DRY constraint and is the exact drift that produced CR-01.

**Rejected — exporting the engine's `defineTiedTeams` and iterating it over the whole
conference to partition every team.** It produces a second grouping authority, and applying
the pull-in rule below the championship slots is an extrapolation the ACC's published policy
does not make ("no other teams may be defined as Tied Teams"). It also changes the bottom of
every table: `winPctSafe` gives a 0-0 team and a 0-2 team the same win percentage, so every
winless team in a conference would share one rank from week 1 onward — a real display
regression, and one the current test at `computeStandings.test.ts:196` was written to
prevent.

**Consequence, stated plainly:** teams the engine did *not* place keep the existing record
convention (win percentage, then wins, then losses, then school, then id) for both their
order and their rank grouping. Two grouping rules coexist — the engine's above, the display
convention below — because the engine only ever opines on the two championship slots and has
no view on 5th versus 6th place. `needsUserInput` seeds contribute no group (D-10: Phase 5
shows no pending state), which keeps today's fallback behaviour for unresolved ties intact.
</design_decision>

| T-05-03-01 | Tampering | `computeStandings` seed-group lookups | medium | mitigate | Rows are built only from `confTeams`; group membership is a Map lookup with a positive-infinity default, so a seed order naming an unknown or out-of-conference id can neither throw nor add a row. | T-05-03-02 | Denial of Service | `computeStandings` sort comparator | medium | mitigate | The comparator is a lexicographic tuple over (group index, then either group position or the record convention), evaluated only within a homogeneous set — a valid total order, so no non-transitive comparator can send the sort into undefined behaviour on adversarial input. |
