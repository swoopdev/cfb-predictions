## Phase Goal

> **ROADMAP goal (verbatim):** Users can see exactly how each conference's championship matchup was determined, see a fully ranked 1..N conference table wherever the tiebreaker procedure can determine an order, and resolve any tie the engine can't settle on its own.

**This plan's slice.** A user opens the standings sidebar and, above each conference's table, reads who is playing in that conference's championship game — by name, from the engine, including the honest half-answer `Georgia vs. one of: Duke / Miami / Clemson` when only one spot is settled.

<objective>
Build the championship matchup element (TIE-07) and give `StandingsTable` the `ranking` prop that both this card and Plan 07's rank markers read from.

D-12 is the load-bearing constraint: the matchup must come from `championshipFor(ranking)` — `groups[0]` and `groups[1]` — and never from standings row order. That rule was written when seed 1 and seed 2 could contradict each other; Plan 02 removed the contradiction, but the rule stands on its own merit, because row order is a display artefact and the seeds are engine facts.

D-13 and D-14 shape the presentation: name the candidates rather than showing a placeholder, and use exactly one presentation for an unsettled seed regardless of cause. 06-UI-SPEC.md §5 is the binding visual contract; the measured group sizes it designs against are a mean of 3.7 and a maximum of 10 at seed 2, which is what makes the overflow rule necessary.

Purpose: TIE-07 — a dedicated, prominent element above each conference's standings table.
Output: `app/components/ChampionshipCard.vue`, a `ranking` prop on `StandingsTable`, and the threading from `useStandings` through `StandingsSidebar`.
</objective>
