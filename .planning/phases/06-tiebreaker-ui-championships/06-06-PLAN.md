## Phase Goal

> **ROADMAP goal (verbatim):** Users can see exactly how each conference's championship matchup was determined, see a fully ranked 1..N conference table wherever the tiebreaker procedure can determine an order, and resolve any tie the engine can't settle on its own.

**This plan's slice.** The explanation itself. A user expands a rank and reads which step separated these teams, what each team's value at that step was, what the procedure tried first and where it restarted — and, when the procedure genuinely ran out and their conference is done, orders the tied teams themselves right there.

<objective>
Build `TiebreakerReasoning.vue` as a self-contained, props-in / events-out component covering TIE-05's reasoning display and D-17's ordering terminus.

It is built and tested standalone in this plan; Plan 07 mounts it inside the standings table and wires its commit event to storage. Building it in isolation is deliberate — it is the phase's most interaction-heavy component, and the plain vitest project can mount it fully with plain props, which is a far better test surface than reaching it through a table.

D-15 puts the reasoning expandable in place, per tied group, inside the standings table rather than in a drawer off the championship card — adjacent to the ranks it explains, and covering every rank rather than only the championship seeds. D-16 governs depth, not completeness: lead with the decisive step, keep everything else one toggle away. D-17 puts the ordering control inside that same expansion, as the terminus of the reasoning, so the user sees exactly what the procedure exhausted before being asked to decide.

Model B is the interaction: the user orders the whole group in one go. 06-RESEARCH.md measured the literal alternative — pick the top, re-run, get stuck on the same group minus one — at 9.23 ACC prompts per fully-picked season versus 3.84 for model B, identical correctness. It does not contradict D-02, whose engine loop is unchanged; only the human's commit granularity differs.

Purpose: TIE-05 in full, plus TIE-06's user-facing half.
Output: `app/components/TiebreakerReasoning.vue` and its test file.
</objective>

4. Component tests stay on the default happy-dom environment and do not import the generated-season harness.

## Two contract details resolved by this plan

**(a) The component renders a panel, not a table row.** 06-UI-SPEC.md §7.1 places the reasoning in a `<tr>` with a single `<td colspan="4">` immediately after the group's last row. `StandingsTable` owns that row and cell because it owns the table structure; `TiebreakerReasoning` renders only the panel `<div>` that sits inside the cell. A component whose root is a `<tr>` cannot be mounted standalone — happy-dom reparents an orphan row — which would forfeit this plan's entire test surface for no gain. Plan 07 supplies the row wrapper.

**(b) The progress line carries both its visible label and its announcement.** 06-UI-SPEC.md §8.2 gives the visible progress copy as a ranked-of-total count while §12.3 gives the live-region announcement as a per-assignment sentence. Both apply to the same node. Resolution: the progress element carries the status role, its visible text is the count, and a visually-hidden span inside the same region carries the announcement sentence, updated on each assignment and replaced by the all-ranked sentence on completion. No third pattern is invented and neither spec clause is dropped.
