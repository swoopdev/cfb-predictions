## Phase Goal

> **ROADMAP goal (verbatim):** Users can maintain multiple independent what-if scenarios side by side, with no account required.

**Planner note (MVP mode):** the ROADMAP `**Goal:**` line for Phase 7 is outcome-shaped but not literally in the `As a … I want to … so that …` user-story form MVP mode expects (no explicit user role, no explicit "so that" outcome clause). It is reproduced verbatim above rather than rewritten, per the "do not invent a story" rule — the synthesized form would be: *as a user predicting the season, I want to keep several independent named what-if picks going at once and switch between them, so that I can compare different guesses without losing any of them or creating an account.* That synthesis is offered only as context; run `/gsd mvp-phase 7` first if the canonical ROADMAP form is wanted before continuing.

**This plan's slice.** Nothing user-visible ships in this plan — it is the load-bearing isolation guarantee every later plan in this phase depends on. After this plan, the three composables that already hold every user's picks, auto-fill provenance, and manual tiebreaker decisions can be asked for a *specific* scenario's data and get back a value that is provably independent of every other scenario's, with zero behavior change for the single-scenario case still in production today.

<objective>
Establish the single source of truth for every scenario-scoped localStorage key (`app/utils/scenarioKeys.ts`), the `ScenarioMeta` type contract (`shared/types/scenarios.ts`), and refactor the three composables that already own persisted user data — `usePicksStorage`, `useAutoFilledGames`, `useManualTiebreakers` — to accept a required `scenarioId` ahead of the existing defaulted `season` parameter.

Purpose: RESEARCH.md's Pitfall 1 is a reproduced, verified defect — passing a reactive scenario id into a single long-lived `useStorage()` call silently leaks one scenario's picks into another. The only safe pattern is a fresh composable call per scenario id, which requires these three composables to accept scenarioId as an argument in the first place. Pitfall 3 is the second load-bearing constraint this plan closes: Plan 07-03's registry composable must build the exact same key strings these three composables use internally for its own duplicate/delete operations, so both sides must share one factory rather than each hand-typing `cfb_<thing>_<season>_<scenarioId>`.
Output: `scenarioKeys.ts`, `scenarios.ts`, and three composables whose signatures and storage keys are scenario-aware, with test coverage proving cross-scenario isolation, unchanged from every other angle.
</objective>
