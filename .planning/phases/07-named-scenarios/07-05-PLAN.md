## Phase Goal

> **ROADMAP goal (verbatim):** Users can maintain multiple independent what-if scenarios side by side, with no account required.

**Planner note (MVP mode):** see Plan 07-01's Phase Goal section for the full discrepancy note on this ROADMAP line's format and the synthesized user-story equivalent; not repeated here.

**This plan's slice.** Everything the phase promised becomes real. A user can open the app, see one migrated scenario holding whatever they'd already picked, create a second scenario, pick different winners in it, switch back to the first, and find their original picks untouched — instantly, with no reload, no login, and no data ever crossing between the two.

<objective>
Wire `useScenarios()` (Plan 07-03) and the two new components (Plan 07-04) into `app/pages/week/[week].vue`, and extract a new `app/components/PicksWorkspace.vue` that owns every scenario-scoped composable call and the picks-dependent half of the page's template, mounted with `:key="activeScenarioId"` so it fully unmounts and remounts on every scenario switch.

Purpose: RESEARCH.md's Pitfall 1 is a reproduced, verified defect in VueUse's `useStorage` — the ONLY safe way to swap which storage instance backs `picks`/`autoFilled`/`standings` is to force a full component remount, never a reactive key into a persisting composable call. Because `week/[week].vue`'s own `<script setup>` runs exactly once per page visit and does not re-run when a template `:key` changes elsewhere in its own template, the scenario-scoped composable calls cannot stay at the page's own top level — they must live inside a component whose OWN instance is what gets keyed. That is the one design decision this plan makes beyond wiring: extracting `PicksWorkspace.vue`.
Output: a user can exercise every one of SCEN-01 through SCEN-05 through the real, running app.
</objective>

**Why a new component is required, not optional.** `usePicksStorage`/`useAutoFilledGames`/`useStandings` currently execute inside `week/[week].vue`'s own `<script setup>`, which runs exactly once per page visit. Putting `:key="activeScenarioId"` on a `<div>` inside that same script's template does NOT cause the script itself to re-run — it only forces the DOM subtree rooted at that div, and every COMPONENT instance within it, to fully unmount and remount. Since `PickProgress`/`PickProgressWeek` also internally call scenario-scoped composables via their own `scenarioId` prop, and a prop value changing does NOT re-run a component's own `<script setup>` either (only a remount does), every one of these calls must live inside components that are themselves descendants of the keyed subtree. The only place currently holding these composable calls is the page's own persisting script — so they must move into a new child component whose mount point in the parent carries the `:key`.
